# 142: Read only the ledger tail in Core's agent service

Status: resolved
Type: task
Published: 2026-10-31
Spec: [DwarfHarness system specification](../spec.md)
Roadmap capability: C3 agent-service scan and reopening cost; ticket 15's fix ruling, answer 5, and its matrix rerun
Blocked by: None (can start immediately)

## What to build

Keep Core's agent service from rescanning the whole ledger on every operation. Ticket [15](15-run-bounded-context-bound-model-and-tool-turns.md)'s labelled diagnostic profiled a loopback run of 12 agents with 20 dormant contexts each and one active turn: 69% of CPU went to whole-history scans, because each scan opens the ledger at the segment start and decodes and hashes every earlier commit before skipping it. The per-wake `Since` page took 47% of CPU, global command lookups from sequence 0 for pre-minted IDs 34% and projection refreshes 10%. The work ran serialized under the service's lock (about 2.9 CPU cores busy, about 16 goroutines waiting on average), and loopback turns took 80–128 s from command to final answer. At two agents the same scripts took 2.4–7.7 s; the cost grows with history size and is multiplied by the number of concurrent turns. Ticket 15's conditional submit adds up to two more full-scan refreshes per refused write.

Reopening is quadratic in the same workload. `acceptCommitLocked`'s reused-command-ID check scans from sequence 0 for every commit whose command ID is below the running maximum, the normal case with concurrent producers. In ticket 15's matrix rerun, the third cell's fresh `Open` had not finished at about 9,400 records when the run's four-hour bound ended it, so the 20×20×3 size never ran.

Use the three remedies the diagnostic names:

- checkpointed tail reads, reusing the ledger reader's checkpoint or an in-memory tail cursor, so that refresh, `Since` and tail scans read only new commits;
- an incarnation command-ID index, so that old-ID checks stop rescanning from sequence 0;
- cold scans moved out of the agent service's lock.

The same command-ID index must remove the quadratic reopening cost. The measurement also reports exchange-token and slot waits read from ledger record times after a cell, not from an observer, as ticket 15's S6 review asked.

## Answer

Four slices replaced the agent service's whole-history scans with the three remedies the ruling chose; no record type, frozen rule, encoding, golden or contract changed.

S1 added a complete incarnation directory of command, turn, tool, refused-effect and paid-attempt occurrences beside the bounded payload cache, built from the ledger at every `Open` and advanced by one publication helper on both commit paths. The reused-command-ID check and the command lookups answer from it with no prefix search; a damaged, stale or disabled directory falls back to the original scan with the same answers and never poisons the service.

S2 keeps Reader checkpoint tokens (D157) in their own bounded class, so payload churn cannot evict them. Refresh is a single-flight streaming read outside `Service.mu` that installs each commit under the lock. `Since` reads from its cursor's token and proves its page end before it mints the next token. Acknowledgement readbacks after a successful `Submit` stay under the lock, because their callers' reservations and completions must become visible together with the commit. S2 also applies the ruling's checkpoint publication rule (amendment 10), which replaces D159's ticket-140 two-site rule from this ticket on. A token is published only by a successful `Open` at its replayed frontier, a contiguous scoped acknowledgement at the new frontier, a refresh that reached the end of its range, a `Since` page or its proof pass that reached its end, or the review readback at its end, and in each case only after that Reader reached its end and closed successfully. Errors, equal bounds, open-ended reads and early stops publish nothing. No decision entry records the rule, because D159 is history only and no standing rule changes (D161).

S3 takes every remaining cold read outside `Service.mu` through one typed protocol of seventeen need kinds. An operation reads unlocked, then revalidates the frontier, its binding and the directory generation before it installs anything or causes an effect. A changed prefix discards every answer read so far and reruns the whole phase, at most twice unlocked, after which it resolves under the lock as before, so no new busy answer, timeout or refusal appears. S3 also rebuilds an invalidated directory from the ledger, at the next refresh that finds the frontier unchanged, and splits commit acceptance into a stage and an install step.

S4 measured the result and documented the costs in the `internal/core/agents` package documentation. By the owner's decision ticket 15's full matrix ran once, on the fixed tree, and passed every gate. The evidence and the package documentation give the detail.

Limits: the cost is O(prefix bytes hashed + suffix decoded), never constant. Every warm page or exact read rehashes its whole containing segment prefix (about 925 KB at 256 padding commands), and [INFERENCE] so does each accepted commit's acknowledgement readback, so write-path hashing grows quadratically within a segment; S4 did not measure that. An additive Reader capability that removes prefix rehashing would be a separate ticket (ruling P1). The command directory is linear in the incarnation's history and never evicted: 96 bytes a selector row and 24 a commit boundary, with container overhead not separately measured and included in the heap figures. Some cold reads stay under `Service.mu`: the third resolution after two unlocked rounds that concurrent writes invalidated; the acknowledgement readbacks after `Submit` with their receipt and duplicate searches, including the case of a lost token; the repeats of task-context, credential-version and private-selection reads when an operation's own commit is accepted; and `Open`'s unpublished replay. The package documentation lists them. The reused-ID check no longer makes reopening quadratic, but the matrix's fresh `Open` still took 45.2 s, 112.8 s, 118.2 s and 109.7 s in its four cells, against 3.2–3.4 s for 4,181 commits in the bounded rows; this ticket did not attribute that remaining time, and the matrix took no profile. The matrix figures are testing-only loopback mechanics under the PaidLimits in force, not provider latency, capacity, isolation, delivery or release evidence. The ledger-time waits are causal envelopes read from record times, not isolated waits. A pre-existing paid-correction defect that the measurement found is outside this ticket (ticket [143](143-let-a-downward-paid-correction-succeed-when-an-admission-names-an-unconfigured-spend-scope.md)). This ticket gives no C3 exit, capacity, latency or isolation proof. C3 status remains solely in its [Status line](../../../docs/ROADMAP-CORE.md#c3-agent-runtime) and [board row](../../../docs/ROADMAPS.md#status-board); contract versions and status remain in the [register](../../../docs/CONTRACTS.md).
