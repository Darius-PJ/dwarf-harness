## What to build

Write the Go art generator, a development program kept in the repository, and use it to produce a small original layered sample with its frame metadata, proving registration, anchors, provenance and reproducible output before the importer is built. The owner reviews the generated map and character sprites before the generator code is approved.

- The generator builds with the pinned toolchain and check command from ticket [01](01-prove-the-portable-toolchain-and-integration-check.md). It uses the Go standard library and, once each has its D29 record, any Go module from outside it that assists sprite generation ([D105](../../../docs/DECISIONS.md#d105-default-fortress-art-go-modules-for-sprite-generation-and-art-rounds-before-the-gui)). It lives with the project's development tools, outside Core, the terminal and the GUI module, and needs no image editor or editor licence ([D103](../../../docs/DECISIONS.md#d103-default-fortress-art-a-go-generator-replaces-aseprite)).
- It is a development tool: it never ships in the GUI, never runs on a user's computer and makes no model call.
- All art comes from version-controlled code, pixel maps, palettes and seeds that agents write; no image-generation model, pre-existing character kit, copied Dwarf Fortress asset or third-party sprite is used, and neither the owner nor users draw or edit pixels.
- Review rounds may study open-source pixel-art and sprite-generation projects for technique and style ([D104](../../../docs/DECISIONS.md#d104-default-fortress-art-pixel-maps-and-owner-review-of-generated-sprites)). None of their art is copied, and reused code follows the dependency rules (D29) and its source licence.

## Acceptance criteria

- [x] The generator deterministically produces a small dwarf part set as separate transparent layers covering every baseline slot (back accessory, body, shoes, legwear, torso clothing, hair/beard, headwear, front accessory), including a hat that occludes hair, skin/hair/clothing palette masks and the reserved overworld role overlay, on 16-pixel overworld and 64-pixel RPG grids.
- [x] The 64-pixel sprites are animation-ready in two views (D108): every part and the assembled dwarves exist straight on, as the still roster frame, and in three-quarter profile with an idle loop and representative role action loops. At least two example Corps show an emblem on a field of their colour, and every view and frame registers with the other layers.
- [x] Every part, variant and frame takes its shape from a pixel map kept in the repository: a text grid in which each character is one pixel. Code rules supply only colors, palette masks, combinations of variants and small seeded texture in rock and floor tiles, so a review comment changes only the parts it names.
- [x] The sample also contains a few rock, floor, wall and door tiles, one station, one stockpile, one rail segment, a dog, and a horse with wheelbarrow, each with a bounded set of motion frames.
- [x] The generator writes transparent untrimmed per-layer PNG frames, or an atlas with explicit source rectangles and offsets, plus JSON metadata giving each frame's rectangle, anchor and layer slot; re-running it with the same inputs, pinned toolchain and module versions reproduces the same files or a documented, explained difference.
- [x] The output's registration, anchors and offsets are inspected and recorded, together with the toolchain version and generator command, as evidence for the importer freeze.
- [x] Licence and provenance records identify the art as original project work produced by the recorded generator version, module versions, inputs and seeds.
- [x] The generator writes two contact sheets, each at 1x and at an integer zoom. The map sheet shows the 16-pixel tiles, props, animals and overworld dwarves in every role, plus a small sample room built from the tiles; the character sheet shows every 64-pixel part, variant, view and frame, plus assembled example dwarves in both views with their Corps markers.
- [x] The owner reviews both contact sheets, and agents turn his comments into changes to pixel maps or rules before they run the generator again. The generator code is approved only after he approves both sheets, and his approval is recorded under Comments.

## Answer

The Go art generator is built and approved. It lives with the project's development tools, builds with the pinned toolchain and check command, uses only the standard library and makes no model call ([D103](../../../docs/DECISIONS.md#d103-default-fortress-art-a-go-generator-replaces-aseprite), [D105](../../../docs/DECISIONS.md#d105-default-fortress-art-go-modules-for-sprite-generation-and-art-rounds-before-the-gui)). From hand-written pixel maps, a palette, colour choices, outfits, a room, animation timings, an example roster and seeds ([D104](../../../docs/DECISIONS.md#d104-default-fortress-art-pixel-maps-and-owner-review-of-generated-sprites)), it renders an original layered sample: 16-pixel map sprites with role markers, tiles, props and animals; 64-pixel character parts in a straight-on still and a three-quarter view with an idle loop and worker and diplomat action loops ([D108](../../../docs/DECISIONS.md#d108-character-sprites-a-still-front-view-an-animated-three-quarter-view-and-corps-emblems-and-colours), [D109](../../../docs/DECISIONS.md#d109-character-sprites-carry-no-role-marker)); two example Corps, each shown as an emblem on a pennant of its colour; untrimmed per-layer frame strips with a draft manifest and a licence and provenance record; and two contact sheets at 1x and 4x with eight loop previews. Its output is byte-reproducible. The owner approved both sheets after three review rounds, and the build advisor approved the code; the assistant decisions of rounds 2 and 3 are recorded in [B19](../../../docs/DECISIONS.md#b19-art-generator-round-2-character-views-page-loops-and-corps-pennants). The approvals, digests and the importer-freeze record are under Comments.
