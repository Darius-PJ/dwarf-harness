## Answer

Ticket 06's share of C2 is built, reviewed and on `main`, and C2 stays In progress. In `internal/core/workspace`, a promotion request carries its own ID: repeating it returns that request's state without a new snapshot, even after a restart, and reusing it for a different request is refused. Each context and workspace may hold four admitted checkpoints, kept in order, so capacity grows with the pairs enrolled, and a fifth request is busy before anything is captured. A request names its scratch's head and is captured against its local parent's sealed tree, never against another context's change queued ahead of it. Core merges each request over its predecessor in the workspace's train with `git merge-tree` under the owner's pinned attributes and records each result as a generation of its own. A conflict at the front of the train ends that request with a report its context can read; a failure ends the requests built on it; another context's failed request only makes the requests behind it rebuild; and a fresh start after a failure takes an explicit new root that reopens no ID. The service writes F2-06's records as the owner froze them (D118). C2's product still admits nothing: `RequestPromotion` answers that no validator exists, and only package tests admit and integrate until C4. Acceptance and moving `main` (ticket 08), temporary scratches (07), policy activation (09), attempts and evidence (C4) and result delivery (C3) remain. [B25](../../../docs/DECISIONS.md#b25-c2-bounded-checkpoints-the-merge-train-and-lineage-outcomes-ticket-06) records the build, including Git 2.45 as Core's floor; Core Appendix A.12 records the admission and integration costs. All of this is verified on Windows; the Linux and macOS rows first run in C3's CI.
