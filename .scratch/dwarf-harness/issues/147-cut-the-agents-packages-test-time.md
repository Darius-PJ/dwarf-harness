# 147: Cut the agents package's test time

Status: resolved
Type: task
Published: 2026-11-21

Blocked by: None (can start immediately)

## What to build

Cut the test time of Core's agent package, `internal/core/agents`, so that its race-detector run fits well under D127's 30-minute per-package limit on all three hosted systems, with room for later growth. Do this without losing or weakening a deliberate-bug (rule-break) or frozen-format (golden) test, changing D127's limits, or skipping a test or taking it out of the hosted check.

The package's race step has grown as C3 tickets landed. On the hosted Windows runner it took 1,478.731 s in run 44471432711 and 1,660.945 s in run 44595543703, both on 2026-11-19; the second passed D127's 25-minute report line. On run 44866294125, ticket [91](91-record-service-loss-and-restoration-for-every-agent.md)'s S2 at 88f4bb6, the race step stopped at the limit (`panic: test timed out after 30m0s`, `FAIL internal/core/agents 1800.653s`). No test had failed, and existing turn-loop tests were still running. The package's tests step, without the race detector, took 1,312.323 s in that run. Run 44874224657, S2's first fix at 8c2c1e2, timed out on Windows the same way. In the same run on macOS, `TestTurnLoopConcurrentPrivateRuntime/openai/shared_memory_cas` failed after 170.24 s with “wrong applied/stale/POST counts”, and the package's race step took 1,512.960 s. Linux passed both runs. By the owner's decision the package's test time is cut rather than the limit raised, and D127's 30-minute limit and 25-minute report line stay (D176).

To build:

1. Measure where the package's test time goes: per-test times in the tests and race steps, setup costs, waits and effective parallelism.
2. From those measurements, a ruled design chooses the changes and their targets before code (D117).
3. Implement the changes.

## Answer

`internal/core/agents`' test time is cut by three slices and one change on ticket 91's branch, chosen from the PM's measurements by a fresh Fable ruling (RulingT147) before code (D117). No contract, record, encoding or golden changed, and no test was removed, skipped or moved.

S1 (test only) runs in parallel the seven turn-loop tests that ran one after another and the crash rows that kill and reopen a child test process (T2), and gives every row that holds a provider exchange open while other turns finish a 30-minute dispatch and transport bound through `raiseDispatchBound`, called in the 16 rows an audit of 19 park sites marked (T5). S2 (test only) builds each golden chapter and paid fixture period once per test process, by the same real sequence, and opens every fixture on its own copy with a real `ledgerstore.Open` (T1); its fix 1 keeps fuzz workers' seeds in a container that the fuzzing coordinator owns and removes after its workers finish. S3 (product) fixes the history index's codec and then fills a released work's entry when its commit is published, so the work stays answerable without a cold read; the [package documentation](../../../internal/core/agents/doc.go) states the fill and the rule that every cached answer survives `encoding/json` both ways. T3, on ticket 91's branch (b3f73b3, rebased as 701337f), builds `FuzzServiceGroupReplay`'s prefixes lazily inside its parallel seeds.

S3 found a defect in ticket 142's code (d9debac): `ledger.Digest` marshals as text and has no inverse, so every cached work entry, and every command entry whose drafts carry `body_refs`, failed to decode and was discarded as a miss. Every lookup of a pruned work therefore folded the history from sequence 0, and prepared answers that carry a typed digest (work answers, commit answers with `body_refs` and turn results) were read three times. Correctness held because every miss folds; no row asserted a hit, which is how the defect stayed hidden. Cached digests now travel as agents-local text, `encodeHistoryCommit` stores records without typed body refs, and the two turn-result folds answer with the result's payload bytes; no contract type gained a method (RuleT147S3).

On the hosted check, the package's race step went from 1,756.6 s on run 44833370745 (`main` before this ticket) to 1,115.5 s on run 44958796872 (S3's landing) on Windows, from 1,370.9 s to 885.7 s on macOS and from 803.4 s to 793.5 s on Linux; its tests step went from 1,198.9 s to 904.5 s on Windows, from 307.8 s to 241.7 s on macOS and from 76.2 s to 118.5 s on Linux. Every ruled hosted target was met on run 44958796872. D179 counts criterion 1 and those targets as met on this ticket's own tree, and ticket 91's S2 lands on its own green run under D127.

T4, running the package's tests eight at a time on Windows, was withdrawn before its owner gate was answered (StandInT147Floor). The check already runs up to four package test binaries at once on the 4-processor Windows runner, sharing one disk, and S1's added overlap slowed the file-heavy packages beside this one: `internal/core/workspace`'s Windows race line rose from 1,027.9 s on run 44833370745 to between 1,332.0 s and 1,478.2 s on runs 44900374699, 44906944738 and 44912316053, and was 1,083.9 s on run 44958796872. T3 missed its ruled 60-s focused bound for `FuzzServiceGroupReplay`; the miss is recorded (D179). With ticket 91's S2, the local race run was also above the ruled final-tree bound.

Limits: with ticket 91's S2 tests added, criterion 1 as first written was out of reach of the two further slices the ruling's floor allowed (StandInT147Floor2), and neither was spent. The large remaining costs sit in classes that earlier decisions protect: D157's per-read ledger reopen and rehash, the per-incarnation directory checks, the flushes the crash rules name, and the Git children of ticket 16's design. On ticket 91's S2 landing run, check 132 (run 44985772136) on 701337f, the package's line in the Windows race step was 1,591.157 s: above criterion 1's 20 minutes as first written and D127's 25-minute report line, inside its 30-minute limit, and reported to the owner under D127; `internal/core/workspace`'s was 1,353.555 s. With that line reached, changing D157's read path is the lasting fix, and the owner's to approve. The ticket closed on the approvals recorded below, the later ones by temporary Claude Opus 5.5 stand-ins (D177); Fable audits it after its reset (D160). This makes no C3 Done claim: tickets 91 and 146 remain, and C3's status is stated only in its [Status line](../../../docs/ROADMAP-CORE.md#c3-agent-runtime) and [board row](../../../docs/ROADMAPS.md#status-board).
