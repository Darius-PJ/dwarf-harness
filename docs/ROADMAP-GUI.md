# Native GUI roadmap

**Status:** operational design and D96 pre-alpha fortress alignment consolidated; the status of GUI and GUI-F is on the [status board](ROADMAPS.md#status-board), and each contract's in [`CONTRACTS.md`](CONTRACTS.md).
**Updated:** 2026-10-08 (D103 Go art generator; D97–D102 ordinary service-loss procedure; D96 consolidation of D89–D95 2026-10-07; prior operational design 2026-10-05).
**Scope:** `dwarf-harness-GUI`, the Fyne native display client in the nested `gui/` Go module. It attaches to the one Core authority for a colony and exposes the same authorized capabilities as the terminal. It is not a second Core, a browser application, a provider client or a credential holder.

## Goal and authority

Build a useful keyboard- and assistive-technology-accessible native client for a DwarfHarness colony. D89–D96 make the owner's Dwarf Fortress reference an explicit tile-based fortress with RPG agent/party inspection and staged team creation. Rooms and dwarves project real identities without owning operational workspace or role state. Use native Fyne v2.8.1 controls and original passive raster art; model output remains plain text/data, never HTML, scripts or executable widget definitions. Visual metaphors imply no permissions or agent properties. D96 is a pre-alpha stopping point, not exhaustive design closure or implementation approval.

The GUI issues only typed C7 commands through the authenticated Core interface. Core enforces every permission, grant, budget, task transition, privacy projection and confirmation. A view or UI role never authorizes an operation. Window close, tab change, disconnect or user leaving the machine cannot stop an active Core host, cancel a turn or withdraw a promotion. The GUI never reads colony files, `.git`, private context directories, credentials, guest exchange areas or raw validation artifacts directly.

Fyne v2.8.1 is selected under delegated engineering authority (B11; BSD-3-Clause). Keep it and all cgo/native graphics dependencies inside `gui/`; Core and terminal remain `CGO_ENABLED=0`. `gui/` imports only the shared frozen contracts and launcher-protocol packages, never internal Core, router, provider, ledger or field packages. Shared schemas remain owned by their contracts; this document does not freeze them. Fyne's native build and platform accessibility behavior are still implementation gates, not established by toolkit selection. [Fyne getting started](https://docs.fyne.io/started/quick/).

The [fortress GUI specification](../.scratch/fortress-gui/spec.md) owns detailed interaction, appearance, creation, building/reconciliation and the full FG01–FG22 native acceptance matrix, retaining FG01–FG15 and adding shared-lifecycle, representative-motion and officer-outage cases. B16 retains Fyne, with Go/Fyne runtime layer composition and passive PNG/manifest assets; D90–D95 supersede its incompatible relationship, autocomplete and cosmetic-history baselines, and D103 replaces its Aseprite selection with a Go generator kept in the repository that writes the default pack. Users may still import local replacement packs. No new game engine, editor or runtime dependency is introduced. Source/license evidence is not generated-art, compositor or native-runtime proof.

## Status and dependency order

The GUI work waits on C7's authenticated local host/session protocol and the separately deliverable C9 backend capability, with Fyne selected. It does **not** wait for whole C9. Keep the cycle-free order:

**C9 backend capability → GUI parity → whole C9 completion**

C9 backend depends on C4, C5 and C6. GUI consumes that backend capability plus C7; it demonstrates GUI parity for those existing typed workflows, and that parity closes whole C9. C7, toolkit selection and backend capability are separate prerequisites, not a single circular C9 dependency. This roadmap claims no implementation, freeze, build, usability study or accessibility result.

The separate **GUI-F fortress/RPG gate** requires actual C3 task/eligibility facts, C6 relationship/memory/publication/handoff evidence, C8 creation/Purpose/alignment/succession capabilities, C9 **backend** pinned alignment execution and corresponding frozen C7 projections/commands/progress/presentation/attach additions. C8's first-action alignment depends on C9 backend, never whole C9 or GUI parity. C3's generic guards and C7 base do not wait backward on C8 or GUI. Optional external-classifier scenarios require actual R5/C10 qualification; a dog drawing is not helper qualification. GUI-A–E retain their existing operational scope: new GUI-F leadership/presentation capabilities do not become prerequisites for GUI-E's independently deliverable C9 parity. Full fortress release additionally requires GUI-F and native accessibility/packaging/resource evidence.

## Product surface

### Fortress and RPG layer (D89–D96)

- A tileset-capable, top-down fortress spanning **z-15 through z+2** inclusive; reserved higher levels remain inaccessible. Exactly one dwarf represents each visible agent, with role colors plus non-color markers, personal Orchestrator/Griot/Diplomat offices, larger Grand offices and worker workshop siderooms around Corps common halls. Diplomats retain clickable offices while gathering in a shared hall, without duplicate dwarves or new communication rights.
- Actual configured classifier-helper associations, including jev or another eligible classifier, appear as dogs in the assisted agent's office/workshop. Animated work, dogs and traffic are cosmetic; Core-reported helper state is not inferred from decoration, geometry or a model name.
- Nearby stockpiles project self-assigned/delegated **waiting tasks**, with ready and blocked work distinguished; active work appears at workshops. They are not inbox/outbox message queues, a stall-age invention or an understaffing diagnosis. Incoming messages use permitted rails; worker-peer and Griot-story routes terminate at the shared board hub, not forbidden private channels.
- Each office rests with a horse and wheelbarrow. On a representative handoff it departs; a replacement fades in after a short cooldown independently of the travelling runner's delivery/fade-out. Batch/rate-limit visible departures instead of animating every event. Actual assignment, delivery and stockpile facts never wait for motion.
- Dwarf, owned-room or workshop inspection opens its own RPG sheet with larger sprite and real scoped, fresh statistics; common areas open the actual Corps party/telemetry. Activity is not achievement. From A's relationship roster, clicking B opens the focused A/B pair with distinct directional labels/memories; selecting either agent from the pair opens that agent's own roster. Keep general, task, board, private relationship memory and delivered shared history separate.
- Relationship labels use the nine trust/sentiment regions below, with unknown outside the grid and partial axes explicit. Signed trust runs -1 distrust, 0 neutral, +1 trust; no missing value becomes a midpoint. A-about-B uses only evidence available to A, not administrator-only knowledge or objective performance grading. Coalesced bounded classification runs automatically on relevant eligible evidence changes through Core admission/accounting, never on opening, hovering or repainting. A last still-authorized label may remain visibly outdated/updating; revoked evidence cannot remain displayed. Numeric bands, evidence rubric, encoding and exact sentiment normalization remain producer/testing work.
- The authenticated colony administrator may inspect all colony records, private memories and both relationship perspectives through Core's administrator projection. This does not impersonate an agent, broaden its recipients or feed administrator-only facts to its classifier. Provider credentials remain Core-held and never enter GUI payloads. Agent/retired-agent views retain their existing D83 restrictions.
- Original modular graphical pixel dwarves/terrain form the default tileset; larger layered RPG sprites share persisted clothing, hair, beard, footwear, accessories and colors. Randomize once, then customize. Tileset changes preserve logical layout and saved appearance IDs; custom packs remain bounded inert licensed content.
- Manual digging/planning remains toggleable (default on); Edit Layout is always available. Build TODO completion enforces floors, correct designation, nonoverlap, functional officer desks/Corps-appropriate worker stations, stockpiles and corridor/stair connections. Enforce officer size/decorative type/count thresholds unless the human disables those size/decorative requirements; functional furniture cannot be waived. Every size preset must fit required furniture. Exact dimensions/counts/footprints remain engineering work. None of these standards gates actual operations.
- Autocomplete offers an informed preview that may rearrange completed rooms. Before replacing redundant furniture in a filled room with required missing types, warn and obtain acceptance. Preserve other customization; no space/invalid fits retain the TODO rather than silently bulldozing or claiming completion. Preserve emptied worker rooms for explicit reuse/move/reclamation; underground demolition fills dirt. Officer-role no-vacancy is a Core lifecycle rule, not room occupancy.
- Terminal-created topology changes prompt on startup/live attach/reconnect even when manual mode is off: Autocomplete, Build manually or Later. Core retains current layout, outfits, blueprints, reviewed topology baseline, creation drafts and partial TODOs across shutdown. Cosmetic undo/history is bounded per GUI run and discarded on close, not permanent per-edit operational history. Stable IDs and version-checked atomic saves prevent duplicate placement or lost work; cosmetic reconciliation cannot create agents or paid work.
- Open CLI uses the existing Core session/context. Prefer a suitable complete off-the-shelf **native** embedded terminal with bounded integration/adaptation within approximately 5–10% of overall-project work; otherwise spawn the user-selected external default terminal. Do not build a bespoke emulator/render/history project. [Terminal research](../.scratch/fortress-gui/terminal-research.md) remains historical candidate evidence with qualification blockers, including scrollback, not adoption, an effort estimate or runtime proof.

### Shared creation, Purpose and succession

- One RPG entry creates a new Corps or one/multiple agents in an existing Corps, from scratch or one/multiple clones. Keep space-first steps discrete, transparent and reversible: designate space, establish shared Purpose, complete exactly one Orchestrator/Griot/Diplomat triad, then add workers and review the exact batch. Final births/one-way doors require explicit reviewed confirmation plus existing Core authorization; changed drafts invalidate approval. Extending a cosmetic boundary is not a birth confirmation. Clones have fresh identities/private contexts and only expressly shareable inheritance; an occupied leadership role cannot silently acquire a second holder.
- Offer **Create** and **Create and activate**. Every new Orchestrator/Griot, including terminal-/agent-born and Grand counterparts, first executes a pinned `grill-with-docs` against the shared Corps/Colony Purpose in its work/values domain. Core enforces this prerequisite; a GUI wizard, unpinned slash command or prompt advice is insufficient. Team onboarding presents Orchestrator then Griot. Warn before creation that even Create-only immediately starts the first paid interview turn under ordinary grants/budgets/admission, then leaves questions waiting without unattended rounds or view-triggered spending.
- Human approval is mandatory for every new leader's initial alignment, including agent-initiated births; a superior model cannot accept it. New Corps ordinary work waits for both approvals, while inspection/alignment remain available and received messages confer no ordinary-work eligibility. Added workers do not restart an aligned Corps. After approval, Create stays ready/inactive; Create and activate proceeds if actual operational gates permit, with no extra mandatory Activate action.
- Keep one mutable Purpose per Corps with role mandates, and a Colony Purpose for Grand leadership—not independent per-agent Purposes. Stage revisions while the current approved Purpose governs work, then cut over after the human decision. Meaningful work/value changes target Orchestrator/Griot re-alignment respectively; corrections do not force interviews. Humans may skip/shorten/disable re-alignment, never new-leader initial alignment. The human chooses completion despite open questions; guidance says stop when questions no longer matter, not exhaust an endless question tree.
- The Orchestrator interview produces a versioned **Corp Creed** containing Purpose, mandates and resolved vocabulary/decisions; the Griot produces a distinct reviewable mythology/origin story. Approved shared artifacts, administrator-inspectable private raw interviews and separately reviewed project exports remain distinct; no automatic repository documentation writes. Terminal and GUI share durable versioned interview progress/approvals and cannot duplicate paid first turns on restart or reattach.
- Prepare and align a non-operational **Aspirant** outside the **Incumbent**'s occupied officer slot. Recipient-authorized handoff covers ongoing processes, lessons and the relationship roster. Deterministic normalized attenuation moves inherited trust/sentiment toward zero, retaining trust more strongly; preserve source/direction and unknown rather than copying values or fabricating zero. Exact function, coefficients, numerical encoding and cutpoints remain open pending testing; the illustrative linear formula is not adopted. No raw private-context, counterpart-memory or grant inheritance follows.
- No occupied officer role becomes vacant without a ready successor. Reviewed Core cutover maintains exactly one holder and retires the predecessor only after successful handover, preserving retired records/private memories; no automatic adviser or early retirement. Service loss follows Core §13.11 (D97–D102): an Incumbent's or Aspirant's service loss pauses succession at its last saved step until restoration, and the owner may declare a lost officer unrecoverable so that a prepared, aligned Aspirant takes over without the live handoff. No GUI emergency bypass, timeout promotion or process-failure-as-handover. Exact readiness and atomic cutover mechanisms remain producer work.
- Grand Griot authors deliberately loose, possibly fictional Colony prehistory; the interview asks/suggests present and future Corps and may explain later arrivals. Corps Griots reinterpret the approved shared version through their own Purpose. Story mention is not birth or approval, and authorized Griot channels/provenance do not expose private boards/interviews. Human approval precedes initial Grand/Corps founding-story publication, but alignment/activation may finish while mythology remains draft; this is neither an activation gate nor blanket approval of all later stories. Fiction is distinct from history, achievements and statistics.
- **Officer outages (D97–D102).** The Corps party sheet shows how many members are paused and how many, and which, reserved questions are waiting, filtered for the inspecting principal; a Grand officer's outage shows on the colony status. Agent sheets show service loss and its cause with a non-color status. Outage begin and end notices arrive without stealing focus, and the owner answers one wait-or-stop prompt per cause, with per-turn overrides and per-turn switch or compact choices. Stand-in controls label every act "the owner, acting for" the office, and the succession view offers the unrecoverable declaration and the restoration-before-cutover choice. Viewing never restores an agent or starts paid work.

These screens retain the operational surfaces below; RPG styling cannot replace actual task, grant, budget, promotion, conversation or workflow facts.

### Colony overview

- Colony name and authorized topology: Corps, role, agent and current context/status, with hierarchy as a textual tree/list as well as an optional operational map pane.
- Current task queue: typed state, assignee/context when readable, dependencies, blocked reason and exact status freshness. Do not render task text or another context's private details unless Core authorizes them.
- Current grants and approvals for the viewed actor/context: scope, resource/budget ceilings, expiration and revocation state. An overview is an explanation, not a grant editor or approval shortcut.
- Resource and BudgetBook view: available/reserved/charged amounts by model/provider, execution capacity, storage and bounded queue/headroom; show units and the revision/time basis. A limit or absence of authorization is visible, never converted to an inferred allowance.
- Promotion train per authorized workspace: durable request order, the caller's own request state and permitted receipts, validation readiness and a generic pending status where generation diagnostics remain sealed for an agent view. Show that a ref move is not acceptance. Agent projections must not expose foreign speculative paths, hashes, checks, logs, identities or verdicts; administrator inspection uses its separate authenticated authority rather than weakening that barrier.
- Permission-scoped resource-pressure and work-overlap hints only if the Core grants that projection (D80). Hints are coarse, audience-bound and content-free.

### Work and conversation panels

- Agent/session/context selector that distinguishes one execution session from its private contexts. Show each view's current context and active turns without merging their transcripts or memory.
- Context/task panel for authorized task description, acceptance criteria, version, exact subject/evidence reference, state changes and blocked reason. Every state-changing action calls the version-checked typed Core command and displays the actual refusal.
- Turn panel for streaming text and bounded live usage/cost statistics. Live text is an ephemeral snapshot/delta stream; it is not promised to survive Core exit. Durable messages/history use the ledger cursor and Core's current audience/read checks.
- Conversation/inbox panel with accepted, delivered, processed and replied status kept distinct; participant membership epoch; read state; authorized attachments; and recipient-specific history. Reading a message never approves a tool or starts a new turn. A retired-agent projection contains only its already-delivered history and private memory, read-only, with sequence holes preserved; no unseen backlog, successor access or future delivery (D83). This does not deny the authenticated administrator's colony-wide inspection.
- Story board lists published Griot versions with source/provenance references and current authorized excerpts. Story text is narrative, not evidence, task completion, law, approval or a worker DM.
- Workflow panel displays the exact pinned C9 graph, run/branch states, gate receipts and bounded loop/escape information. Run/edit/continue actions are typed commands and are reauthorized by Core at execution.

Every panel filters through current Core principal/projection authorization. Reconnect, search, selection changes, notifications, accessibility announcements, clipboard/export and attachment retrieval cannot bypass that filter. Administrator inspection may expose all colony records/private memories through the administrator projection, never by impersonating the viewed agent or leaking provider credentials; agent views and classifier inputs retain their own narrower permissions.

## Interaction and accessibility requirements

- Every operation is reachable and usable with keyboard alone, with visible focus, stable tab order, mnemonic/shortcut documentation, non-destructive defaults and explicit confirmation for irreversible or scope-changing operations. No mouse-only drag/drop requirement.
- Expose meaningful accessible names, roles, values, relationships, descriptions and state-change announcements for native controls and dynamic lists. Announce status changes without moving focus. Verify on every supported OS with actual screen readers and accessibility inspectors; toolkit APIs alone are not proof of assistive-technology support.
- Do not convey status by color alone: pair icon/shape and explicit text with color; preserve readable contrast, scaling, zoom and system text-size behavior. Do not depend on hover for essential detail.
- Respect reduced-motion settings and provide static equivalents for animated workshops, dogs and representative traffic. Bound/coalesce animation work, pause offscreen motion and preserve all actual state without motion or autoplay narratives.
- Provide clear pending, busy, unavailable, permission-denied, stale, interrupted and disconnected states with a retry or explanation only where Core provides one. A retry cannot invent automatic command replay: the same immutable idempotency key is only for the same command, and expired/stale cosmetic retries must be refused rather than reapplied.
- Keep focus, selection and the reader's current location stable when a list refreshes. Announce insertions/removals and respect read/unread state without scrolling a user unexpectedly.

The fortress pane has a synchronized textual tree/list and keyboard-accessible building/creation tools. D89–D96 select original fortress/RPG art and construction semantics; exact art/palettes and footprint-qualified presets remain engineering work, with role markers, contrast and native-accessibility gates. Neither color nor pointer-only tile interaction may be the only way to identify or operate an agent.

## State, rendering and reconnect contract

1. Launch with explicit detached `dwarf-harness --host --no-terminal` when no Core host is available, wait for authenticated readiness, then attach to the existing host. `run/host.json` is a discovery hint, never proof of host identity. Reopening a colony reuses its single GUI instance; a view reconnect cannot start another Core or duplicate an agent loop.
2. Negotiate C7 protocol version, authenticate colony/session/context, and request an authorized initial state snapshot with a durable `through_seq`. Keep an independent cursor per GUI view. Resume only from that view's cursor; if the Core reports a gap or snapshot requirement, replace state from the authorized snapshot and continue after its high-water sequence.
3. Render live turn text from snapshot plus deltas after the supplied `delta_high_water`. On a text gap, request a fresh snapshot. Do not persist the stream or silently present it as durable conversation history.
4. Commands include a UUIDv7 idempotency key and expected object revision where applicable. A changed command must have a new ID. Show the Core's durable receipt/state; local optimistic UI may not imply accepted promotion, completed task, granted permission or successful check.
5. Apply the Core's authorization before rendering, caching, reading aloud, announcing, searching, exporting or copying sensitive content. Do not store a broader local history/cache than the active authorized projection. Disconnect clears transient/private buffers when current authority cannot be re-established.
6. Bound every list, transcript, live delta buffer, attachment preview, graph and diagnostic by configured row/byte/page caps. Use cursor pagination and virtualized rows; fetch the next authorized page on demand. Never append an unbounded colony history to a widget or automatically expand arbitrary generated text.
7. Render model/tool/memory content only as plain text with safe native label/text widgets; approved passive sprite/tileset assets use the separate bounded art pipeline. Link-like content is inert unless a typed safe URI action is explicitly authorized; no HTML, remote resource load, shell link or executable widget is interpreted.
8. Presentation saves use typed C7 commands and Core's sole durable writer/storage discipline, never a GUI database or direct colony-file write. Atomically save layout/appearance/blueprints and related TODO progress before reporting Saved; keep cursor, reviewed topology baseline and pending placement distinct. The producer must specify replaceable/bounded presentation snapshots/checkpoints and finite cosmetic retry retention, with expected revisions, stale/expired-command refusal, authorization, crash recovery and explicit unsaved/conflict states. Current saved state survives close; bounded per-run undo does not. Operational birth/alignment/Purpose/approval/publication/succession history remains retained append-only. The feature spec defines required behavior without freezing this storage mechanism.

D63 remains passive: completion notifications create no model/provider call. A reader may explicitly invoke a normal authorized action. The GUI can disconnect while Core work continues. Agent-facing result surfaces use the same BD2 whole-generation barrier as terminal and status APIs; administrator inspection remains a distinct authenticated Core projection, not a weakened agent-view privacy boundary.

## Roadmap gates

### GUI-A — Native shell and host attach (waits for C7)

Build a Fyne application in `gui/`, one instance per colony. Start/attach to the detached Core using C7; display booting, recovering, ready, quiescing, stopped and unavailable states from authenticated protocol events. Verify that closing/reopening the view leaves Core and an in-flight turn alive, and that a second launch attaches instead of duplicating the colony client. No GUI-side fallback Core or local ledger.

### GUI-B — Durable/live client (waits for C7)

Implement independent `through_seq` cursor, authorized snapshot/gap recovery, ephemeral live-text high-water/deltas, typed idempotent commands and explicit disconnect/stale/error states. Verify actual host restart and reconnect behavior once C7 implementation exists. Persist no transcript or authority projection as an alternative source of truth.

### GUI-C — Operations and privacy projections (waits for C7; C9 panels wait for C9 backend)

Deliver the existing operational colony/Corps/roster, context/task, grants/approvals, resource/BudgetBook, promotion train, conversation/history/story and typed workflow surfaces through actual C7 producers; later GUI-F creation/alignment/succession extensions do not gate GUI-C/E parity. Exercise each available command through Core and show its exact outcome, never fabricated producer data. Verify principal/role/context denial across list, search, reconnect, notification, accessibility, clipboard and attachment paths, especially agent-view foreign speculative validation and retired history; separately verify administrator inspection without impersonation or credential exposure. Workflow graph/run display consumes the C9 backend as soon as that capability is delivered.

### GUI-D — Accessibility and usable operation (requires GUI-A–C)

Run keyboard-only task flows, screen-reader/name-role/value/state checks, focus/announcement checks, non-color status, scaling/contrast and reduced-motion checks on every supported OS. Verify that bounded/virtualized lists remain navigable and stable under live updates and reconnect. Record OS, Fyne/runtime version, screen reader and tested workflows; do not label support from static review alone.

### GUI-E — C9 parity and packaging (requires GUI-D, C7 and C9 backend)

Show that a user can inspect, run and track the same authorized pinned recipe/workflow/branch/loop/escape state in terminal and GUI without a second graph model, authority engine, wallet or run state. Test stale graph revision, revoked edge, inaccessible attachment, required branch failure, capped-loop escape and duplicate completion through the real Core API. GUI-E's parity evidence is the GUI input to **whole C9 completion**; C9 must not be a prerequisite for starting GUI-E.

Package separately from Core: Windows GUI and Core executables; macOS signed/notarized GUI and separately signed virtualization helper where applicable; Linux package with its documented Fyne/graphics dependencies. Core and terminal remain cgo-free. Pin toolchains, toolkit, native helper and package identities; no runtime compiler download. Ship the Fyne BSD-3-Clause notice. Installation, package size, cold start, idle CPU/RAM, high-update behavior and accessibility remain measured release gates, not current facts. The macOS VM executor remains its own B11/D87 helper and execution profile, not bundled as a GUI-only requirement. For the first release only the Windows packages are required; the macOS and Linux packages follow it (D138).
